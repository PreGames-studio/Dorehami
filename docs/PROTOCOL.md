# پروتکل دورهمی — گوشی‌ها چطور حرف می‌زنند

> **خلاصهٔ فارسی:** همهٔ ارتباط‌ها (بلوتوث و اینترنت) **یک نوع پیام** دارند: «پاکت» (Envelope).
> همین باعث می‌شود یک بازی هیچ‌وقت نداند روی بلوتوث اجرا می‌شود یا اینترنت، و ما بتوانیم بعداً
> مسیر ارتباطی جدید اضافه کنیم بدون دست‌زدن به بازی‌ها. این سند شکل دقیق پاکت، پیام‌ها، خطاها و
> قواعد سازگاری را می‌گوید.

---

## ۱. پاکت (Envelope)

```jsonc
{
  "v": 1,                       // نسخهٔ پروتکل — ناهمخوانی = رد صریح، نه رفتار عجیب
  "id": "e_ab12cd34ef56",       // شناسهٔ پیام (برای پاسخ خطا و ack)
  "ts": 1791476000000,          // ساعت فرستنده — فقط تشخیصی؛ هرگز مبنای تصمیم نیست
  "type": "session.action",     // یکی از Msg.*
  "room": "4QP6R",              // کد اتاق
  "from": "p_x1y2z3",           // فرستنده (اسمی؛ هویت واقعی از سوکت می‌آید)
  "to": null,                   // null = همهٔ اتاق؛ وگرنه شناسهٔ یک بازیکن
  "seq": 42,                    // شمارهٔ ترتیب که «مرجع» تعیین می‌کند (وضعیت/رویداد)
  "payload": { }                // بدنهٔ مخصوص همان type
}
```

قواعد پاکت:

* `explicitNulls = false` (پاکت کوچک — روی بلوتوث مهم است)، `ignoreUnknownKeys = true`
  (نسخهٔ قدیمی اپ با پیام جدید کرش نمی‌کند؛ برای کاربر ایرانی که دیر آپدیت می‌کند حیاتی است).
* حداکثر اندازهٔ یک پاکت ۱۶KB و یک بستهٔ فریم‌شده ۲۴KB است.
* **هویت:** مرجع هرگز به `from` اعتماد نمی‌کند. هر سوکت به یک هویت بسته است (سرور: از توکن؛
  بلوتوث: از دست‌دادن لابی). `from` فقط برای تشخیص و لاگ است.

## ۲. فهرست پیام‌ها

| گروه | نوع | فرستنده → گیرنده | کار |
|---|---|---|---|
| sys | `sys.hello` | همه → همه | معرفی اولیه: نسخه، اتاق، شناسهٔ من |
| sys | `sys.ping` / `sys.pong` | هردو طرف | زنده‌بودن و اندازه‌گیری تأخیر |
| sys | `sys.error` | هردو طرف | خطا با کد و ارجاع به پیام خطادار |
| lobby | `lobby.join` | مهمان → مرجع | درخواست نشستن روی صندلی |
| lobby | `lobby.ack` | مرجع → مهمان | تأیید + کد اتاق + وضعیت صندلی + لیست اعضا |
| lobby | `lobby.rejected` | مرجع → مهمان | رد عضویت (اتاق پر، بازی شروع شده) |
| lobby | `lobby.roster` | مرجع → همه | هر تغییر لیست صندلی‌ها |
| lobby | `lobby.ready` | مهمان → مرجع | اعلام آمادگی |
| lobby | `lobby.start` | مرجع → همه | شروع بازی: بازیکنان، گزینه‌ها، زمان شروع |
| lobby | `lobby.leave` / `lobby.kick` | هردو | خروج / بسته‌شدن اتاق |
| session | `session.state` | مرجع → همه | وضعیت عمومی (view، نوبت، مهلت، شمارهٔ ترتیب) |
| session | `session.private` | مرجع → یک نفر | اطلاعات خصوصی او (دست/کلمه/نقش) + حرکات مجاز |
| session | `session.action` | بازیکن → مرجع | حرکت من |
| session | `session.event` | مرجع → همه | رخداد (فید بازی، صدای رابط کاربری) |
| session | `session.resync.request` | بازیکن → مرجع | «برگشتم، وضعیتم را بفرست» |
| session | `session.resync` | مرجع → یک نفر | وضعیت کامل + اطلاعات خصوصی |
| session | `session.finished` | مرجع → همه | پایان بازی + رتبه‌بندی + رکورد |
| chat | `chat.message` / `chat.emoji` | همه → همه | چت و واکنش سریع |

نکتهٔ امنیتی: در `session.action` هویت فرستنده **از سوکت** خوانده می‌شود، نه از داخل پیام. پس
تقلب «من جای نفر دیگر بازی می‌کنم» ساختاراً بسته است.

## ۳. بدنهٔ پیام‌های مهم

```jsonc
// lobby.join
{ "player": { "id": "p_a1b2", "displayName": "سارا", "avatarId": "default" },
  "resume": false, "version": 0, "appVersion": "1.4.0" }

// lobby.ack
{ "ok": true, "roomCode": "4QP6R", "roomName": "اتاق سارا", "gameId": "hokm",
  "seat": 2, "isHost": false, "members": [ { "player": {…}, "seat": 2, "ready": false, "connected": true, "isHost": false } ] }

// lobby.start
{ "matchId": "m_9f8e7d", "gameId": "hokm", "options": { "targetPoints": 7, "turnSeconds": 30 },
  "players": [ {…}, {…}, {…}, {…} ], "startedAtMs": 1791476000000 }

// session.state  (view = اطلاعات عمومی بازی؛ نوبت و مهلت برای تایمر رابط کاربری)
{ "view": { "round": 1, "trump": "SPADES", "turn": "p_c3d4", "trick": [], "cardsLeft": { "0": 13, … } },
  "seq": 87, "phase": "PLAYING", "turn": "p_c3d4", "deadlineMs": 1791476030000 }

// session.private  (view = فقط مال خودم؛ actions = حرکت‌هایی که همین حالا مجازم)
{ "view": { "hand": [ { "suit": "H", "rank": "7" }, … ] }, "seq": 87, "actions": [ "play_card" ] }

// session.action
{ "type": "play_card", "payload": { "suit": "H", "rank": "7" } }

// session.finished  (record = فقط سرصفحه؛ لاگ کامل حرکت‌ها در پاکت ۱۶KB جا نمی‌شود و نزد مرجع/سرور می‌ماند)
{ "result": { "matchId": "m_9f8e7d", "ranking": [ { "player": "p_a1b2", "seat": 0, "rank": 1, "points": 7 } ],
              "digest": "sha256:…" },
  "record": { "schema": 1, "seed": 99123871, "gameId": "hokm", "players": [ … ], "actionCount": 412, "digest": "…" } }
```

## ۴. فریم‌بندی روی بلوتوث

بلوتوث پیام بزرگ را یک‌تکه قبول نمی‌کند؛ پس لایهٔ `transport/nearby` پیام را می‌شکند و طرف مقابل
بازچینی می‌کند. بقیهٔ سیستم این را نمی‌بیند («پیام کامل، کامل تحویل داده می‌شود»).

سرصفحهٔ ۱۰ بایتی هر تکه:

| بایت | معنی |
|---|---|
| ۰ | امضای فریم = `0x44` |
| ۱ | نسخهٔ فریم‌بندی = ۱ |
| ۲–۳ | شمارهٔ پیام (u16) |
| ۴–۵ | شمارهٔ این تکه (از ۰) |
| ۶–۷ | تعداد کل تکه‌ها |
| ۸–۹ | طول این تکه (u16) |

قواعد بازچینی: تکهٔ معیوب/تکراری نادیده گرفته می‌شود؛ اگر پیامی ۱۵ ثانیه ناتمام بماند دور ریخته
می‌شود (جلوگیری از انباشت حافظه)؛ شمارندهٔ شناسه پس از ۶۵۵۳۵ به ۱ برمی‌گردد.

## ۵. کدهای خطا (بخشی از قرارداد)

```
proto.version | proto.malformed | proto.too_large | proto.unknown_type
room.not_found | room.full | room.closed | room.in_progress
auth.unauthorized | auth.token_expired | auth.not_in_room
game.illegal_action | game.not_your_turn | game.unknown_player
game.bad_options | game.bad_payload | game.bad_state
transport.peer_timeout | transport.closed | server.internal
```

رابط کاربری روی **کد** تصمیم می‌گیرد و پیام فارسی خودش را نشان می‌دهد (مثلاً `room.full` →
«اتاق پر است»). متن پیام سرور فقط برای دیباگ است و هرگز مبنای منطق رابط کاربری نیست.

## ۶. قواعد سازگاری و نسخه‌بندی

1. فیلد جدید **همیشه** مقدار پیش‌فرض دارد؛ فیلد حذف نمی‌شود، فقط «بی‌استفاده» می‌شود.
2. نوع پیام ناشناخته **نادیده** گرفته می‌شود، نه خطا (سازگاری رو به جلو).
3. هر تغییر ناسازگار ⇒ `PROTO_VERSION` یکی جلو می‌رود و مرجع نسخهٔ ناهمخوان را با
   `proto.version` رد می‌کند (کاربر پیام «نسخهٔ برنامهٔ شما با میزبان هم‌خوان نیست» می‌بیند).
   **وضعیت پیاده‌سازی امروز (ثبت‌شده در ADR-0007):** `Envelope.decode` پیام با `v` ناهمخوان را
   رد می‌کند، ولی میزبان کد `proto.malformed` می‌فرستد و مهمان بی‌صدا رد می‌کند — کد
   `proto.version` تعریف شده و هنوز در هیچ مسیری استفاده نمی‌شود. اصلاح تشخیصی و مذاکرهٔ نسخه
   در handshake کار HK-032 است.
4. کدهای خطا هرگز تغییر معنی نمی‌دهند؛ کد جدید اضافه می‌شود.
5. سیاست کامل نسخه‌بندی (رکورد، قواعد، RNG، پروتکل)، مدل تهدید و روش مهاجرت:
   `docs/adr/ADR-0007-versioning-rules-rng-record-protocol.md`.

## ۷. مسیرهای سرور (خلاصه — پیاده‌شده در `server/Application.kt`)

```
GET  /healthz                     زنده‌بودن + تعداد اتاق‌ها/منتظرها
POST /v1/auth/guest               توکن مهمان (HMAC بدون حالت؛ /v1/auth/telegram بعداً)
GET  /v1/games                    فهرست بازی‌ها + تنظیمات پیش‌فرض
POST /v1/rooms                    ساخت اتاق خصوصی (کد ۵ حرفی بدون 0/O/1/I/L)   [Bearer]
GET  /v1/rooms/{code}             وضعیت اتاق
POST /v1/rooms/{code}/join        اجازهٔ ورود (پر/شروع‌شده ⇒ 409) و مسیر سوکت    [Bearer]
POST /v1/matchmaking              ورود به صف حریف تصادفی                        [Bearer]
GET  /v1/matchmaking/{id}?wait=20 انتظار (long-poll) برای حریف؛ بعد از ۲۵ ثانیه اتاق با ربات
DELETE /v1/matchmaking/{id}       انصراف
GET  /v1/matches/{code}           رکورد کامل قابل بازپخش (seed + لاگ + digest)
WS   /v1/ws/room/{code}?ticket=… سوکت اتاق — از این لحظه همه‌چیز Envelope است
```

شروع بازی روی سرور با پیام `lobby.start` از طرف صاحب اتاق (اولین عضو) روی همان سوکت انجام می‌شود،
نه با مسیر HTTP جدا. سرور یک `HostController` بدون صندلی است؛ یعنی دقیقاً همان منطق میزبان بلوتوثی.
