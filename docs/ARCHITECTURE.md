# معماری دورهمی (Dorehami)

> سند مرجع معماری. هر تغییری در ساختار پروژه باید اول اینجا بیاید، بعد در کد.
> نسخه: ۱.۰ — مهر ۱۴۰۵

## ۱. دورهمی در یک نگاه

دورهمی یک اپ اندروید است که همهی بازیهای دورهمی را در یکجا جمع میکند: بازیهای ورق (حکم)،
بازیهای فکری (شطرنج)، بازیهای تیمی و نمایشی (پانتومیم، مافیا) — و هر بازی جدیدی که بعداً اضافه
شود. سه راه بازی وجود دارد و **هر سه از یک کدِ قواعد استفاده میکنند**:

| حالت بازی | مسیر ارتباط | «مرجع» (کسی که وضعیت را در دست دارد) |
|---|---|---|
| آفلاین (بدون اینترنت) | بلوتوث / وایفای دایرکت (Nearby Connections) | همان گوشیای که اتاق را ساخته |
| آنلاین (اتاق خصوصی یا حریف تصادفی) | WebSocket به سرور خودمان (VPS ایرانی) | سرور |
| تکنفره / تمرینی | ارتباطی لازم نیست | خود گوشی |

نکتهی کلیدی معماری: **سرور یک نسخهی دوم از بازی نیست.** سرور هم برای هر اتاق دقیقاً همان
`SessionController` و `GameEngine` را اجرا میکند که گوشیِ میزبانِ بلوتوثی اجرا میکند؛ فقط «لوله»
عوض میشود (بلوتوث ↔ وبسوکت). نتیجه: هر قاعدهی بازی که یکبار نوشته و تست شود، در آفلاین و آنلاین
و تکنفره یکسان است و هیچ باگ «فقط در حالت آنلاین» وجود ندارد.

```
                       ┌──────────────────────────────────────────┐
   ┌───────────────┐   │              اپ اندروید                  │
   │  بازی ۱: حکم  │   │  app (ناوبری، پروفایل، دیآی)             │
   ├───────────────┤   │  games/<بازی>/ui  (صفحهی هر بازی)        │
   │ بازی ۲: پانتومیم│  │  core/uikit (تم، RTL، اجزای مشترک)        │
   ├───────────────┤   └────────────────┬─────────────────────────┘
   │ بازی ۳: شطرنج │                    │ (فقط این لایه به رابط کاربری وصل است)
```

## ۲. تصمیم زبان و پلتفرم (چرا Kotlin، چرا نه وب)

| گزینه | حکم | دلیل |
|---|---|---|
| **Kotlin + Jetpack Compose (انتخاب‌شده)** | ✅ | بلوتوث آفلاین در اندروید فقط از طریق APIهای بومی (Nearby Connections) درست کار میکند؛ وب نمیتواند رادیو بلوتوث را اداره کند. Compose برای بازیهای ورق/تخته با انیمیشن و RTL ایرانی عالی است. یک زبان برای گوشی، سرور و بازیها = یک تیم کوچک سهنفره میتواند همهجا کار کند. |
| وب/PWA | ❌ | نه بلوتوث آفلاین، نه دسترسی به مخاطبین/نوتیفیکیشن بومی، نه کیفیت انیمیشن لازم؛ و در ایران Burden نصب/PWA پایین نیست. |
| Flutter | ❌ | بومی بلوتوث ضعیفتر، و اشتراک کد با سرور (Kotlin) از دست میرود. |
| Unity | ❌ | برای بازیهای ورق/تخته سنگین و گران است؛ APK بزرگ؛ تیم سهنفره درگیر موتور میشود نه بازی. |

**آینده:** چون هسته (`core/*`) هیچ وابستگی اندرویدی ندارد (خالص Kotlin/JVM)، بعداً میتوان بدون
بازنویسی همان هسته را با Kotlin Multiplatform به iOS/دسکتاپ/وب برد — i.e. UI عوض میشود، قواعد نه.

## ۳. مرزهای ماژولها (قانون طلایی)

```
core/protocol    ← قالب پیام: Envelope، Msg، خطاها، فریمبندی، شناسهها        (وابستگی: هیچ)
core/gamesdk     ← قرارداد بازی: GameModule/GameSession/GameEngine + قطعیت     (وابستگی: protocol)
core/session     ← چرخهی اتاق: SessionController + پیامهای لابی/نشست          (وابستگی: gamesdk)
core/testkit     ← فیکهای درونحافظه برای تست سریع                             (وابستگی: session)
core/uikit       ← تم Compose، RTL، اجزای مشترک UI                             (وابستگی: Android)
transport/api    ← «لوله»: GameTransport + رویدادها + پیکربندی                 (وابستگی: protocol)
transport/nearby ← پیادهسازی بلوتوث/وایفای دایرکت                              (وابستگی: api)
transport/online ← پیادهسازی وبسوکت + کلاینت صف رندوم                          (وابستگی: api)
games/X/core     ← قواعد یک بازی + ربات + تست                                   (وابستگی: gamesdk)
games/X/ui       ← صفحههای همان بازی                                           (وابستگی: games/X/core, uikit)
server           ← داور آنلاین: HTTP + سوکت اتاق + صف + ذخیرهسازی              (وابستگی: games/*)
app              ← ناوبری، دیآی، لابی، تنظیمات                                 (وابستگی: همه)
```

سه قاعدهی ممنوعه:

1. **هیچ بازیای به بازی دیگر وابسته نمیشود.** یک بازی = یک پوشه، قابل واگذاری به یک توسعهدهنده.
2. **`core/*` هیچوقت به بازی یا سرور وابسته نمیشود** (جهت وابستگی همیشه به سمت پایین است).
3. **سرور و اپ منطق بازی ندارند**: هر چیزی که «قاعده» است در `games/X/core` است؛ هر چیزی که
   «چرخهی اتاق» است در `core/session`.

معیار سنجش این مرزها در CI: اگر ماژول `games/chess` را حذف کنیم، هیچچیز جز فهرست ثبت بازیها
نشکند.

## ۴. قراردادهای هسته (قلب معماری)

### ۴.۱ یک بازی چه چیزی را باید پیاده کند

```kotlin
interface GameModule {                       // «آنچه بازی دربارهی خودش میگوید»
    val meta: GameMeta                       // نام، تعداد بازیکن، تیمی/انفرادی، قابلیتها
    fun defaultOptions(): JsonObject         // تنظیمات پیشنهادی اتاق
    fun validateOptions(options: JsonObject): JsonObject   // اعتبارسنجی تنظیمات میزبان
    fun create(config: GameConfig): GameSession            // ساخت نشست از یک سید
    fun preferredPartySize(): Int = meta.minPlayers        // برای پر کردن اتاق در بازی رندوم
    val botAction: ((GameSession, PlayerId) -> GameAction?)? // سیاست ربات (اختیاری)
}
```

### ۴.۲ نشست بازی، خالص و قطعی

```kotlin
interface GameSession {
    val phase: Phase                     // SETUP / PLAYING / FINISHED
    val version: Long                    // شمارهی وضعیت (برای همگامسازی و anti-cheat)
    fun apply(player: PlayerId, action: GameAction): ApplyResult   // Ok(releaseها) | Rejected(code)
    fun publicView(): JsonObject         // آنچه همه میبینند (بدون دست/کلمه/نقش دیگران)
    fun privateView(player: PlayerId): JsonObject  // آنچه فقط خودِ بازیکن میبیند
    fun legalActions(player: PlayerId): List<String>
    fun result(): MatchResult?           // جدول پایانی
    fun snapshot(): JsonObject           // وضعیت کامل (برای ذخیره/ادامه)
}
```

**قاعدهی قطعیت (Determinism):** قواعد بازی تابعی خالص از `(سید، لاگ حرکات)` هستند. هیچ بازیای
حق ندارد `System.currentTimeMillis()` یا `Random()` صدا بزند؛ زمان از `Clock` و تصادف از `Rng`
تزریقشده میآید. به همین دلیل:

* یک بازی را میتوان بعد از بستهشدن برنامه **دقیقاً از همانجا ادامه داد**؛
* هر بازی را میتوان **بازپخش** کرد و به همان مقدار هش (digest) رسید؛
* تستها بدون `sleep` و بدون flake نوشته میشوند.

### ۴.۳ موتور: تنها نویسندهٔ وضعیت

`GameEngine` حلقهی رسمی است: `apply()` حرکت را به نشست میدهد، لاگ میگیرد، نسخه را جلو میبرد و
«انتشار»ها را پخش میکند:

```kotlin
sealed interface Emission {
    data class Public(val type: String, val payload: JsonObject)         // برای همه
    data class Private(val to: PlayerId, val view: JsonObject)           // فقط برای یک نفر
    data class Feed(val key: String, val args: JsonObject, val kind: String) // رخداد خوانا در فید
    data class Sound(val name: String)                                   // افکت صوتی UI
}
```

نکتهی حساس اطلاعات پنهان: دستِ هر بازیکن فقط از مسیر `Emission.Private` میرود و در
`publicView()` هیچوقت ظاهر نمیشود؛ تست هر بازی این را «ساختاری» میسنجد (مثلاً کلید `hand` برای
بقیه غایب است، نه فقط خالی).

### ۴.۴ لاگ حرکات و رکورد قابل اثبات

```kotlin
data class LoggedAction(val seq: Long, val player: String, val type: String,
                        val payload: JsonObject, val atMs: Long)

data class MatchRecord(               // تنها قالب ذخیرهسازی کل پلتفرم (schema=1)
    val gameId: GameId, val seed: Long, val options: JsonObject,
    val players: List<PlayerId>, val actions: List<LoggedAction>,
    val result: MatchResult?, val digest: String, val schema: Int = 1
)
```

پس از پایان بازی، رکورد (`سید + لاگ + نتیجه + هش`) ذخیره میشود. هر کس — سرور، داور تورنمنت، یا
اپلیکیشن — میتواند همان رکورد را **بازپخش** کند و ثابت کند نتیجه دستکاری نشده:

```kotlin
val engine = GameEngine.replay(module, record)   // همان موتور، از سید
verdict = MatchVerifier(registry).verify(record) // Verified(نتیجه, هش) | Rejected(دلیل)
```

**وضعیت پیاده‌سازی امروز:** رمزگذاری/رمزگشایی این قالب در `MatchRecordCodec` (لایهٔ مشترک) است و
`GET /v1/matches/{code}` از همان استفاده میکند. بازی محلی هم پس از هر حرکت رکورد را ذخیره و با
بازپخش قطعی بازیابی میکند؛ رکوردِ ناشناخته/خراب/نسخهٔ جدیدتر **رد امن** میشود (نه کرش).
`MatchVerifier` امروز فقط در تستهای قطعیت صدا زده میشود و سیمکشیِ تأیید در مرجع سرور باقی است.
سیاست نسخه‌بندی (رکورد، قواعد، RNG، پروتکل)، مدل تهدید RNG و روش مهاجرت:
`docs/adr/ADR-0007-versioning-rules-rng-record-protocol.md`.

## ۵. پروتکل (یک پاکت، همهکاره)

همهی ارتباطها — بلوتوث و وبسوکت — یک نوع پیام دارند: `Envelope`. این «تکپاکتی» بودن باعث میشود
هیچ بازیای نداند روی چه لولهای اجرا میشود و بتوانیم بعداً لولهی جدید (WiFi Direct، سرور
محلی) اضافه کنیم بدون لمس بازیها.

```jsonc
{ "v": 1,                    // نسخه پروتکل (ناهمخوانی = رد صریح، نه رفتار عجیب)
  "id": "e_ab12…",           // شناسه پیام (برای پاسخ خطا و acks)
  "ts": 1791476000000,       // ساعت فرستنده — فقط برای تشخیص، هرگز مبنای تصمیم نیست
  "type": "session.action",  // یکی از Msg.*   (sys.* | lobby.* | session.* | chat.*)
  "room": "4QP6R",           // کد اتاق
  "from": "p_x1…", "to": null,   // null یعنی «همهی اتاق»
  "seq": 42,                 // شماره ترتیب که مرجع تعیین میکند
  "payload": { }             // بدنهی مخصوص همان type
}
```

* **فریمبندی:** روی بلوتوث پیامها به قطعههای ≤۲۴KB شکسته و سمت مقابل بازچینی میشوند (سرصفحهی
  ۱۰بایتیDorehami با نسخه و شماره)؛ در وبسوکت خودش تکهتکه نمیکنیم.
* **خطاها کد دارند** (`room.full`, `game.not_your_turn`, …) و رابط کاربری روی همان کد پیام فارسی
  نشان میدهد («اتاق پر است»)، نه روی متن.
* **سازگاری رو به جلو:** فیلد ناشناخته نادیده گرفته میشود؛ پس نسخهی قدیمی اپ با پیام جدید سرور
  کرش نمیکند (برای کاربران ایرانی که دیر آپدیت میکنند حیاتی است).

## ۶. `SessionController` — یک کلاس، چهار نقش

این کلاس تمام «چرخهی اتاق» را میچرخاند و همهجا یکسان است:

| نقش | ترنسپورت | مرجع وضعیت |
|---|---|---|
| میزبان آفلاین | nearby (بلوتوث) | خودش |
| مهمان آفلاین | nearby | میزبان |
| مهمان آنلاین | online (وبسوکت) | سرور |
| سرور (میزبان آنلاین) | server-room | خودش |

مسئولیتها: دست دادن لابی (`join`/`ack`/`roster`/`ready`/`start`)، پخش وضعیت و اطلاعات خصوصی،
اعمال نوبت و **تایمر نوبت**، درایو صندلیهای ربات (از سیاست خودِ بازی)، پینگ/پونگ و تشخیص قطعی،
و **ریسینک** وقتی کسی برمیگردد (`session.resync.request` → وضعیت کامل + دست خصوصی).

```kotlin
val controller = SessionController(transport, registry, clock)
controller.host(HostOptions(gameId = "hokm", self = me, roomCode = "4QP6R",
                            authorityOnly = false))       // سرور این را true میکند
controller.submit("play_card", jsonOf("suit" to "H", "rank" to "7"))
controller.state.collect { ui -> render(ui) }             // یک StateFlow، یک منبع حقیقت برای UI
```

`SessionUiState` تنها اسنپشاتی است که رابط کاربری میخواند (فاز، لیست صندلیها، دست من، نوبت کیست،
مهلت، جدول امتیاز، فید، آخرین ردِ حرکت). UI هیچوقت به موتور یا ترنسپورت مستقیم وصل نمیشود.

**رباتها:** رباتها بازیکنِ درجهیک هستند (صندلی واقعی، لاگ واقعی، همان قواعد). سیاست حرکت آنها
را خود بازی میدهد (`GameModule.botAction`) و مرجع (گوشی میزبان یا سرور) آن را اجرا میکند. بدون
تزریق RNG و زمان ⇒ بازپخش بازی با ربات هم دقیقاً همان نتیجه را میدهد.

## ۷. لایهٔ ارتباط: `transport/api` و دو پیادهسازی

```kotlin
interface GameTransport {                 // «لوله»
    val state: StateFlow<TransportState>  // CLOSED/STARTING/CONNECTED/DEGRADED/FAILED…
    val peers: StateFlow<List<PeerInfo>>
    val events: Flow<TransportEvent>      // PeerFound/PeerConnected/PeerDisconnected/Notice
    val incoming: Flow<TransportPacket>   // پیامهای کامل و بازچینیشده
    suspend fun open(config: TransportConfig): Result<OpenInfo>
    suspend fun send(target: PeerId?, data: ByteArray): Result<Unit>
    suspend fun broadcast(data: ByteArray): Int
    suspend fun close()
}
```

سه تضمینِ قرارداد (که تستهای مشترک آنها را میسنجند): `incoming` همیشه پیام کامل میدهد؛
`broadcast` به همه جز خودمان میفرستد؛ قطع شدن یک نفر رویداد `PeerDisconnected` میدهد (هیچوقت
سکوت و سکون).

* **`transport/nearby` (بلوتوث آفلاین):** تبلیغ اتاق با `roomCode` و `capacity` در اطلاعات تبلیغ،
  کشف + اتصال خودکار مهمان، بازچینی فریمها، و مدیریت اذن/خاموشی رادیو (نسخههای جدید API از
  برنامه میخواهند وضعیت رادیو را خودش مدیریت کند ⇒ کد ما شکستِ رادیو را Notice میکند، نه کرش).
* **`transport/online`:** وبسوکت با تیکت توکن؛ همان `Envelope`ها. تشخیص قطعی و بازگشت خودکار با
  ریسینک.

## ۸. سرور (داور آنلاین)

سرور همان کد بازی را اجرا میکند، پس «داور» بودنش یعنی:

```
POST /v1/auth/guest            → توکن مهمان (یا /v1/auth/telegram با initData تلگرام)
GET  /v1/games                 → فهرست بازیها + قابلیتها + تنظیمات پیشفرض
POST /v1/rooms                 → ساخت اتاق خصوصی (کد ۵ حرفی)
POST /v1/rooms/{code}/start    → شروع بازی (سازندهٔ اتاق یا عضو نشسته)
GET  /v1/rooms/{code}          → وضعیت اتاق (فاز، صندلیها، آنلاینها)
POST /v1/matchmaking/queue     → صف بازی رندوم
GET  /v1/matchmaking/{id}?wait=20 → انتظار long-poll برای حریف/اتاق
POST /v1/matches               → ارسال رکورد بازی: بازپخش + تأیید/رد
GET  /v1/stats                 → آمار و بازیهای اخیر
WS   /v1/ws/room/{code}?ticket=… → سوکت اتاق (همهچیز از این به بعد Envelope است)
```

اجزای داخلی:

| جزء | کار |
|---|---|
| `RoomHub` | دفتر اتاقها. هر اتاق = یک `RoomTransport` (کانال سوکتها) + یک `SessionController` با `authorityOnly=true` (سرور خودش صندلی نمیگیرد). |
| `Matchmaker` | صف به تفکیک بازی؛ بهاندازهی دلخواه همان بازی (`preferredPartySize`) که رسید اتاق میسازد؛ اگر کسی نرسد بعد از مهلت با ربات پر میکند (وگرنه بقیه معطل میشوند). |
| `MatchStore` | در حالت توسعه درونحافظه، در تولید Postgres (Hikari + Flyway + JDBC ساده). فرمت = `MatchRecord` (jsonb) تا هم تاریخچه باشد هم سند اثبات. |
| `MatchVerifier` | بازپخش رکورد و مقایسهی هش/جایگاهها؛ مبنای «آمار قابل اعتماد» و تورنمنت. |
| صفحهٔ وضعیت `/` | HTML تکفایلی RTL با آمار زنده (بدون CDN) — برای چک سریع روی VPS. |

تنظیمات فقط از متغیر محیطی (`DOREHAMI_PORT`, `DOREHAMI_TOKEN_SECRET`, `DOREHAMI_DB_URL`, …) تا
هیچ رمزی در گیت نباشد. توکنها HMAC-SHA256 خودماناند (`v1.<payload>.<sig>`، ۳۰ روز) — JWT لازم
نداشتیم و بعداً جایش قابل تعویض است.

## ۹. جریانهای کامل (سناریوها)

**الف) اتاق بلوتوثی (آفلاین، بدون اینترنت):**
میزبان: `RoomHub` در گوشی نیست، خود `SessionController.host()` روی ترنسپورت nearby → تبلیغ اتاق →
بقیه در صفحهٔ «بازی آفلاین» کد/نام را میبینند → اتصال → `lobby.join` → تأیید → آماده → «شروع» →
میزبان موتور را میسازد و وضعیت + دست خصوصی هرکس را میفرستد → حرکات به میزبان میآید، میزبان
اعتبارسنجی و پخش میکند → پایان بازی، رکورد ساخته و ذخیره میشود.

**ب) اتاق آنلاین با کد (دوستان):**
هر کس توکن میگیرد → سازنده `POST /v1/rooms` → کد را در گروه میفرستد → بقیه `join` روی سوکت →
سرور (که خودش میزبان است) همان چرخه را میچرخاند.

**ج) بازی رندوم تیمی:**
`POST /v1/matchmaking/queue` → صف سرور → بهمحض رسیدن تعداد → اتاق ساخته میشود و کد به همه اعلام
→ همه به سوکت همان اتاق وصل میشوند → اگر کسی نیامد، بعد از ۱۲ ثانیه با ربات پر میشود (تنظیمشدنی)
→ همان جریان ب.

**د) تکنفره/تمرینی:** بدون ترنسپورت، `GameEngine` مستقیم با رباتها؛ همان تستها.

## ۱۰. اعتماد و ضدتقلب (بدون سرور سنگین)

1. **انتسابِ فرستنده:** مرجع هرگز به هویت اعلامشدهی داخل پیام اعتماد نمیکند؛ هر سوکت به یک
   `playerId` بسته است (روی سرور: از توکن؛ روی بلوتوث: از دستِ دادن لابی).
2. **مالکیت انحصاری وضعیت:** فقط مرجع state را تغییر میدهد؛ همهی حرکات از `apply()` میگذرند و
   نامعتبر با کد رد میشوند.
3. **اثبات با بازپخش:** رکورد (`سید + لاگ`) قابل بازپخش است ⇒ هر ادعای نتیجه در جدولهای امتیاز و
   تورنمنتها با `MatchVerifier` راستیآزمایی میشود.
4. **اطلاعات پنهان ساختاری:** تستها تضمین میکنند دستِ دیگران در view عمومی نیست (نه اینکه خالی
   باشد — اصلاً نباشد).

## ۱۱. افزودن یک بازی جدید (چرا با سه نفر جواب میدهد)

```
games/mygame/core/
  MyGameModule.kt      object MyGameModule : GameModule { … }
  MyGameSession.kt     قواعد
  MyGameBots.kt        سیاست ربات (قطعی)
  build.gradle.kts     فقط :core:gamesdk
  src/test/…           تست قواعد + تست نشت اطلاعات + تست بازپخش
games/mygame/ui/
  MyGameScreen.kt      صفحهی Compose با core/uikit
```

سپس فقط **دو خط** در کل پروژه: ثبت در `GameRegistry` اپ و در `ServerGames` سرور. لابی، صف رندوم،
تورنمنت، آمار، تماشاچی و ضدتقلب خودکار برداشته میشوند. مالکیت: هر بازی کامل در اختیار یک
توسعهدهنده است و مرزِ «قانون طلایی» تضمین میکند سه نفر همزمان بدون تداخل کار کنند.

## ۱۲. کار تیمی سهنفره و عاملهای هوش مصنوعی روی گیتهاب

* **مالکیت:** هر توسعهدهنده یک بازی (و پوشهٔ خودش). سه مسیر مشترک (`core`, `server`, `app`) با
  برچسب `core/*` و بازبینی دو نفره.
* **قرارداد تغییرناپذیر:** APIهای `core/gamesdk` و `core/protocol` فقط با ADR و ورژنبندی تغییر
  میکنند؛ بازیها نباید بشکنند.
* **LEADER.md در ریشهٔ مخزن:** 👑 رهبر این گروه «گلپا» است. هر کسی برنچ می‌سازد، PR/ایشو می‌زند یا
  فایلی (خصوصاً فایل‌های `.md`) را ویرایش می‌کند، باید اول این فایل را بخواند و در **اولین پیام**
  بنویسد: «👑 رهبر شما گلپا است؛ می‌تونید کارتون رو ادامه بدید.» تأیید نهایی هر ادغام با گلپاست؛
  ورک‌فلوی `.github/workflows/leader-greeting.yml` همین پیام را خودکار می‌گذارد.
* **AGENTS.md در ریشهٔ مخزن:** نصب/ساخت/تست/معیار Done/ممنوعیتها — همان چیزی که هر عامل
  (Copilot coding agent، Claude Code، Cursor، Codex) اول میخواند. این فایل عمداً ابزارمحور نیست.
* **Issue = تسک یک عامل:** هر ایشو دقیقاً یک ماژول را هدف میگیرد، «فایلهای ممنوعه» را نام میبرد،
  و «تعریف انجام» را با دستور تست مشخص میکند. مثال برچسبها: `game/hokm`, `core/session`,
  `docs`, `good-first-issue`.
* **CI:** `./gradlew checkAll` (تست همهٔ ماژولهای JVM + سرور) روی هر PR؛ خروجی تستها بهصورت XML
  برای بررسی ماشینی.

## ۱۳. وضعیت واقعی مخزن

این بخش باید با فایل‌های موجود در همین شاخه هماهنگ بماند؛ متن‌های تاریخیِ اجرای یک محیط دیگر،
معیار موفقیت ساخت یا تست این checkout نیستند.

* در نقطهٔ شروع این شاخه، `core/*`، `transport/*`، `server` و بازی‌های دیگر جای‌نگهدار بودند؛
  اپ اندروید Compose فقط خانه، انتخاب بازی و تنظیمات پایه داشت.
* `games/pantohub/core` اکنون شامل مدل و موتور محلی قطعی، انتخاب واژهٔ تزریق‌شده، اعتبارسنجی
  فارسی، کُدک CSV و snapshot JSON است؛ تست‌های JVM برای قواعد و بانک نوشته شده‌اند.
* `games/pantohub/ui` اکنون صفحهٔ راه‌اندازی/بازی، تاریخچه/آمار و مدیریت محلی بانک را فراهم
  می‌کند؛ بانک با SQLite محلی نگه‌داری می‌شود و از فایل‌های CSV/JSON ورود و خروج می‌گیرد.
* seed آزمایشی اکنون ۱٬۰۰۰ رکورد فارسیِ دست‌چین‌شده و یکتا دارد؛ این **بانک ۲۰٬۰۰۰ رکوردی نیست**
  و هدف کامل نشده است. اعتبار ساختاری/فارسی، یکتایی نرمال‌شده و توزیع سطح‌ها با
  `scripts/validate_pantohub_seed.py` کنترل می‌شود. ارتقای seed نسخهٔ دوم تراکنشی و افزایشی است:
  ردیف‌های موجود یا دادهٔ واردشده بازنویسی نمی‌شوند و فقط ردیف غایب درج می‌شود. ورود فایل، رکورد
  تازه را تا بازبینی انسانی قابل‌بازی نمی‌کند.
* اتصال ابری/حساب کاربری در مخزن تنظیم نشده است؛ همگام‌سازی بین دستگاه‌ها فعال نیست.
* وضعیت ساخت/تست این شاخه باید از خروجی واقعی همان اجرا گزارش شود. اگر JDK 17 یا Android SDK
  در محیط موجود نباشد، Gradle اجرا نشده محسوب می‌شود، نه سبز.

## ۱۴. افزودهٔ معماری پانتومیم (محلی و آفلاین)

درخواست محصول پانتومیم، مسیر محلی را پیش از تکمیل زیرساخت عمومی بازی‌ها مجاز کرده است. این یک
استثنای مستند برای عرضهٔ یک مسیر عمودی آفلاین است؛ ادعای تکمیل `GameModule`، اتاق بلوتوث/آنلاین،
یا پذیرش نهایی کل نقشهٔ راه نیست.

* **پلتفرم:** Android + Kotlin + Jetpack Compose؛ PWA انتخاب نشد، چون تصمیم معماری اصلی، اپ بومی
  آفلاین و قابلیت‌های اندرویدی است.
* **منطق:** `games/pantohub/core` یک reducer قطعی است. ساعت monotonic/epoch و واژهٔ تصادفی به‌صورت
  ورودی از لایهٔ UI/ذخیره‌سازی می‌آیند؛ خود قواعد نه ساعت سیستم می‌خوانند و نه RNG.
* **وضعیت:** نسخهٔ snapshot‌دار بازی مرجع وضعیت است؛ همهٔ عملیات بازی نسخه‌دارند تا رویداد تکراری
  امتیاز دوباره ثبت نکند. تایمر از deadline monotonic محاسبه می‌شود؛ epoch فقط برای تاریخچه و
  بازیابی پس از reboot پشتیبان است.
* **داده:** `games/pantohub/ui` از SQLite داخلی Android برای بانک و تاریخچه استفاده می‌کند؛ بانک
  روی `normalized_text` یکتا است، برای فیلتر index دارد و هیچ وابستگی DB جدیدی اضافه نشده است.
  SQLite انتخاب شد چون در checkout فعلی Room وجود نداشت و پشتیبانی پایدار ۲۰٬۰۰۰ رکورد بدون
  افزودن وابستگی و بدون نگه‌داری بانک بزرگ در preferences را می‌دهد. مقداردهی seed با نسخهٔ
  `curated-bootstrap-v3` (۲٬۵۰۰ رکورد) فقط ردیف‌های غایب را درج می‌کند تا نصب نسخه‌های قبلی بدون برخورد کلید ارتقا یابد.
* **ظاهر پانتومیم:** تم کاغذیِ گرم، سبز تیره و برنجی با نقش‌های هندسی کم‌رنگ فقط در محدودهٔ پانتومیم
  اعمال می‌شود؛ قاب عمومی صفحه defaultهای سازگار دارد تا ظاهر سایر بخش‌های اپ تغییر نکند.
* **نام بازیکنان:** پروفایل محلی همچنان بر پایهٔ نام نرمال‌شده بازیابی می‌شود، اما حضور تکراری یک
  نام در چند تیم شناسهٔ مستقلِ جایگاه در همان roster می‌گیرد؛ بنابراین موتور می‌تواند دو انسان
  هم‌نام را بدون خطای شروع بازی بپذیرد.
* **پنهان‌سازی:** واژه فقط در صفحهٔ اختصاصی اجراکننده دیده می‌شود؛ دکمهٔ پوشاندن فوری دارد و
  هنگام آشکاربودن، Android `FLAG_SECURE` برای جلوگیری از screenshot و snapshot تعویض برنامه فعال
  است. هنگام خروج یا بازیابی فرایند نوبت pause و واژه پوشانده می‌شود؛ مهلت گذشته از clock معتبر
  بررسی و بسته می‌شود. این کار محرمانگی فیزیکی روی گوشی مشترک ایجاد نمی‌کند و رابط
  محدودیت را یادآوری می‌کند.
* **آمار فردی:** ذخیره و تجمیع آمار بازیکن opt-in است؛ در حالت خاموش، شناسه و نام بازیکن در رخداد
  نوبت ذخیره نمی‌شود، اما آمار تیمی باقی می‌ماند.
* **مرحلهٔ بعد:** پس از پیاده‌سازی و تثبیت `core/gamesdk`، adapter پانتومیم باید به قرارداد عمومی
  بازی و `SessionController` وصل شود؛ تا آن زمان قابلیت شبکه/ربات ادعا نمی‌شود.

**محدودیت محصول:** دادهٔ ۲۰٬۰۰۰تایی باید از منبع دارای مجوز و قابل‌بازبینی گردآوری/اعتبارسنجی
شود. تولید مصنوعی برای پُرکردن شمارنده ممنوع است؛ بنابراین نسخهٔ فعلی عدد واقعی را نشان می‌دهد و
بانک را کامل معرفی نمی‌کند.
