# HK-014 — سفر کاربر، طرح کم‌جزئیات و برنامهٔ پژوهش

**وضعیت:** ✅ DONE (2026-10-16) — تحویلِ Docs/Prototype. **اجرا نشده:** پژوهشِ واقعی با کاربران ۴۵+/۶۰+ (نیازمند دسترسی به کاربران واقعی؛ این محیط فاقد آن است — طبق قاعدهٔ نقشهٔ راه، «انجام‌نشده» ثبت می‌شود، نه «تست‌شده»).

## ۱. سفر کاربر (User Journey)

```
ورود (HokmEntry)
  ├─ تنظیم: نام، تعداد بازیکن (2/3/4)، امتیاز هدف، سطح ربات، صدا، لرزش
  ├─ دکمهٔ «بلوتوث»  → LobbyScreen (اتاق محلی)
  ├─ دکمهٔ «آنلاین»   → LobbyScreen (اتاق آنلاین)
  └─ «شروع با ربات»   → HokmScreen (بازی محلی)
        │
        ▼
میز بازی (HokmScreen + HokmTable)
  ├─ تعیین حاکم (۵ کارت) → انتخاب حکم
  ├─ پخش بقیهٔ کارت‌ها
  ├─ بازی ترفند‌ها (با تایمر نوبت در اتاق)
  ├─ بنر پایان دست / کُت / حاکم‌کُت
  └─ بنر پایان مسابقه
        │
        ▼
نتیجه (HokmScreen — Game Over)
  ├─ نمایش امتیاز/برنده
  ├─ دکمهٔ «دستِ قبلی» (↶) برای مرور
  └─ «بازی دوباره» / «خروج»
```

## ۲. طرح کم‌جزئیات (Low-Detail Wireframe)

### ۲.۱ صفحهٔ ورود (HokmEntry)
- هدر: لوگو + کارنامه (بازی/برد/کُت/دست) + دکمهٔ پاک‌کردن.
- فرم: نام (TextField)، تعداد بازیکن (Segmented 2/3/4)، امتیاز هدف (1/3/5/7)، سطح ربات (pro/easy)، صدا (switch)، لرزش (switch).
- دکمه‌های اصلی: «شروع با ربات» (پررنگ)، «بلوتوث»، «آنلاین» (کم‌رنگ‌تر).
- کفِ لمسی ۴۸dp برای همهٔ اهداف (HK-013).

### ۲.۲ میز بازی (HokmScreen)
- مرکز: نمد (TableBackground) + کارت‌های وسط (currentTrick).
- پایین: دستِ بازیکن (فشرده، قابل انتخاب).
- بالا/چپ/راست: حریف‌ها (آواتار + تعداد کارت + امتیاز).
- نوار امتیاز (بالا): تیم/نفر، امتیاز، هدف؛ ضربه → برگهٔ امتیاز (هر دست).
- گوشه: دکمهٔ ↶ (دستِ قبلی)، دکمهٔ تنظیمات سریع.
- بنرها: تعیین حاکم، پایان دست، کُت، پایان مسابقه (از HokmChoreography).

### ۲.۳ حالت‌های خالی/خطا (GX-07 — برش‌های بعدی)
- بدون اتصال، بدون حریف، timeout نوبت، خطای شبکه — هرکدام با پیامِ فارسی قابل اقدام (نه کد خطا).

## ۳. برنامهٔ پژوهش (Research Plan)

### ۳.۱ گروه‌های هدف
- **۴۵+** (بزرگسال/سن‌بالا) — گروه اصلی.
- **۶۰+** (سالمند) — گروه حساس (قلم بزرگ، کنتراست، reduced motion).

### ۳.۲ سؤالات پژوهش
1. آیا کاربر ۴۵+ می‌تواند بدون آموزش، حکم و خال را تشخیص دهد؟ (نشانهٔ درشت + چهاررنگ)
2. آیا ترفند/دست/مسابقه را در UI از هم تشخیص می‌دهد؟ (واژگان HK-008)
3. آیا تایمر نوبت (۳۰s) استرس ایجاد می‌کند یا کافی است؟
4. آیا reduced motion (کاهش حرکت) تجربه را بهتر یا بدتر می‌کند؟
5. آیا صداها (card_play/card_cut/your_turn) کمک یا مزاحمت‌اند؟

### ۳.۳ روش
- آزمونِ قابلیت استفاده (usability) با ۵–۸ نفر در هر گروه.
- سناریوی ثابت: یک مسابقهٔ کامل با ربات (از HokmBaselineScenario).
- معیارهای کمّی: زمانِ تکمیلِ اولین ترفند، تعدادِ خطای غیرمجاز، SUS (System Usability Scale).
- معیارهای کیفی: think-aloud، مصاحبهٔ پس از آزمون.

### ۳.۴ خروجیِ مورد انتظار
- لیستِ اولویت‌بندی‌شدهٔ مشکلات (P0/P1/P2) با شاهد.
- تصمیمِ محصولی برای هر مشکل (اصلاح/تعویق/رد).
