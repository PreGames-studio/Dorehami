## ۱. ماتریس دستگاه‌های مرجع

ROADMAP §10.2 «دستگاه» را این‌طور خواسته: حداقل یک دستگاه اقتصادی (~۳GB RAM)، یک میان‌رده، و یک
دستگاه جدید؛ مدل و Android دقیق در خط پایه ثبت شود؛ صفحهٔ کوچک/بزرگ و چرخش/تغییر اندازه آزموده شود.

| شناسه | پروفایل لازم | مدل دقیق | Android / API | RAM | رزولوشن | وضعیت |
|---|---|---|---|---|---|---|
| `DEV-LOW` | اقتصادی، حدود ۳GB RAM، صفحهٔ کوچک/معمولی | *پر شود* | *پر شود* | *پر شود* | *پر شود* | ❌ تأمین نشده |
| `DEV-MID` | میان‌ردهٔ متداول بازار ایران (هدف اصلی ۶۰fps) | *پر شود* | *پر شود* | *پر شود* | *پر شود* | ❌ تأمین نشده |
| `DEV-HIGH` | دستگاه جدید/پرچم‌دار (سقف توان) | *پر شود* | *پر شود* | *پر شود* | *پر شود* | ❌ تأمین نشده |
| `EMU-API24` | emulator برای `minSdk=24` (قدیمی‌ترین API پشتیبانی‌شده) | AVD | Android 7.0 / API 24 | — | — | ❌ تأمین نشده |
| `EMU-API36` | emulator برای `targetSdk=36` | AVD | Android 16 / API 36 | — | — | ❌ تأمین نشده |

قواعد ثبت:
1. نام مدل بازاری **و** `ro.build.fingerprint` هر دو نوشته شوند (`adb shell getprop ro.build.fingerprint`).
2. هر عدد در §۷ با شناسهٔ دستگاه، نسخهٔ build (`git rev-parse --short HEAD`) و تاریخ ثبت می‌شود؛ عدد بی‌شناسه پذیرفته نیست.
3. دستگاه‌ها قبل از اندازه‌گیری ۱۰ دقیقه بی‌کار می‌مانند (دمای پایدار)، روشنایی ثابت، و فقط اپ حکم در پیش‌زمینه.

## ۴. روش اندازه‌گیری — دستورها و خروجی لازم

هر اندازه‌گیری با این سه‌گانه ثبت می‌شود: **دستگاه (§۱) + commit + سناریو (§۲)**. بدون هر سه، عدد
قابل استناد نیست.

### ۴.۱ آماده‌سازی مشترک

```bash
git rev-parse --short HEAD                      # ثبت commit
adb shell getprop ro.build.fingerprint          # ثبت دستگاه
./gradlew :app:assembleDebug && adb install -r app/build/outputs/apk/debug/app-debug.apk
adb shell am force-stop ir.dorehami.app
adb shell settings put global animator_duration_scale 1   # و برای آزمون کاهش حرکت: 0
adb shell dumpsys deviceidle disable            # اختیاری: پایداری اندازه‌گیری
```

### ۴.۲ فریم (روانی میز)

```bash
adb shell dumpsys gfxinfo ir.dorehami.app reset     # صفر کردن شمارنده‌ها
# سناریوی FOUR_PLAYER را از گام ۰ تا ۳۹۳ با سرعت ثابت پخش کن (§۶: هارنس دستگاه)
adb shell dumpsys gfxinfo ir.dorehami.app > gfx-DEV-MID-<commit>.txt
```

خروجی لازم: از بخش `Framestats`/`Total frames rendered` این چهار عدد استخراج و در §۷ ثبت شود —
`p50`, `p95`, `p99` زمان فریم (ms)، درصد فریم‌های `>32ms`، و `Janky frames`. معیار پذیرش:
`p95 ≤ 20ms` و `frms>32ms < 1%` روی `DEV-MID`.
برای دقت بیشتر (و تفکیک UI thread از RenderThread) یک trace هم گرفته شود:

```bash
adb shell perfetto -o /data/misc/perfetto-traces/hokm.pftrace -t 30s sched freq gfx view
```

### ۴.۳ حافظه

```bash
adb shell dumpsys meminfo ir.dorehami.app > mem-start-<commit>.txt
# سناریو پخش شود؛ سپس ۱۰ چرخهٔ «ورود به میز → خروج»
adb shell dumpsys meminfo ir.dorehami.app > mem-end-<commit>.txt
```

خروجی لازم: `TOTAL PSS` و `Java Heap` در ابتدا و انتها، و **روند** ۱۰ چرخه (یک عدد در هر چرخه).
مقبول است اگر `TOTAL PSS < 250MB` باشد و روند ۱۰ چرخه صعودیِ یکنواخت نداشته باشد (شیب ≈ ۰).

### ۴.۴ شروع سرد


خروجی لازم: `TotalTime` هر بار ⇒ **میانهٔ ۵ بار** ثبت شود (نه میانگین، تا دورریز پرت نباشد).

دیداری انتخاب کارت. خروجی لازم: p95 روی ۲۰ ضربهٔ متوالی در سناریوی ثابت.

### ۵.۳ ممیزی کد — دو شکاف واقعی که پیدا شد ❌

1. **کاهش حرکت (reduce motion) هیچ hook ندارد.** در کل مخزن هیچ ارجاعی به `ValueAnimator.areAnimatorsEnabled()`،
   `areTransitionsEnabled()` یا `Settings.Global.ANIMATOR_DURATION_SCALE` نیست (grep ⇒ صفر نتیجه).
   انیمیشن‌ها از `animateFloatAsState`/`rememberInfiniteTransition` با `tween(...)` ثابت می‌آیند، پس
   با خاموش‌کردن انیمیشن در تنظیمات دستگاه **همه** حرکت‌ها از بین می‌روند (که قابل قبول است)، ولی
   اپ مسیر «حذف انیمیشن‌های غیرضروری، حفظ خوانایی» را که ROADMAP §10.2 خواسته **پیاده نکرده**.
   ⇒ کارت پیشنهادی: **IMP/HK-013.a** (به §۹ نگاه کن).
2. **۲۵ جعبه با ارتفاع `dp` ثابت دور متن.** متن‌ها `sp` هستند (۵۸ مورد) پس با مقیاس قلم بزرگ

   `FeedChip`)، دکمهٔ «خروج» (`width(74.dp)`) و `Spacer`های ثابت می‌توانند در `fontScale=200%`
   متن را **ببرند**. این یک ریسک اندازه‌گیری‌نشده است: تا آزمون واقعی روی دستگاه، ادعای «قلم
   ۲۰۰٪ سالم است» نمی‌شود. ⇒ در §۵.۴ به عنوان نخستین آزمون دستگاه ثبت شد.

## ۸. یافته‌های اندازه‌گیری/ممیزی در همین مرحله

این‌ها چیزهایی هستند که **با اجرا یا ممیزی واقعی** به دست آمدند، نه حدس:

1. بیشترین کارت در دست در هر دو سناریو **۱۳** است؛ حالت «۱۷ کارت» در ROADMAP §10.2 با قواعد
   فعلی دونفره تولید نمی‌شود ⇒ سناریوی مرجع آن حالت را پوشش نمی‌دهد و اگر روزی قواعد تغییر کند،
   اثرانگشت عوض می‌شود و تست خبر می‌دهد.
2. **کاهش حرکت hook ندارد** (§۵.۳-۱) و **۲۵ ظرف با ارتفاع `dp` ثابت** دور متن `sp` هست (§۵.۳-۲).
3. «حالت سبک» که بودجهٔ ۳۰fps به آن بسته شده، **در کد کلید/مسیر ندارد**؛ پس بودجه‌اش امروز
   قابل اندازه‌گیری نیست (نه اینکه اندازه‌گیری شده و رد شده باشد).
4. footprint منابع حکم **۰٫۸۳MB** است — دو مرتبهٔ بزرگی زیر بودجهٔ ۳۰MB.
5. `MatchVerifier` (از ADR-0007) هنوز در پروداکشن سیم‌کشی نشده ⇒ «اثبات نتیجه» در خط پایهٔ
   عملکرد نقشی ندارد؛ این ربطی به HK-013 ندارد ولی برای تفسیر نتایج ثبت می‌شود.
6. سناریو آن‌قدر سبک است (۵۵ms) که می‌تواند داخل `checkAll` بماند؛ یعنی **هر PR** خط پایه را
   از نظر قطعی‌بودن کنترل می‌کند، نه فقط اجراهای دستی.
